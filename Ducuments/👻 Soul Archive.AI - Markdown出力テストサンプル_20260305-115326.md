結論から言うと、原因は **「改行（hard line break）」と「段落」の Markdown ルール＋保存時の空白処理**が混ざって壊れている可能性が高い。

カイエが貼ってくれたログを見ると、実際にこういう構造になっている。 

```
これは同一段落の文章です。␠␠  ここで改行しています。␠␠  しかし段落は続いています。
```

ここで問題になっているのは **真ん中の行**。

```
␠␠
```

つまり

```
(スペーススペース + 改行)空行
```

が入っている。

Markdown的にはこれが **完全に別物**。

### 正しい「改行（hard break）」

```
文章A␠␠文章B
```

→ 同一段落の改行

### 今起きている状態

```
文章A␠␠(blank line)文章B
```

→ **段落が分離される**

# なぜこうなるか

ほぼ確実にこのどれか。

### 1️⃣ 保存処理が `trim()` している

多くのテキスト整形コードで

```
line.trim()
```

を使うと

```
␠␠
```

の行が

```
""
```

になり **空行になる**。

### 2️⃣ DOM → Markdown 変換で `<br>` が二重変換

ChatGPTのDOMは実際には

```
<p>text<br>text</p>
```

になっている。

これを変換すると

```
text␠␠text
```

にするべきところを

```
text␠␠text
```

にしてしまう実装が多い。

### 3️⃣ 改行生成ロジックが

```
line + "  \n\n"
```

になっている

本来は

```
line + "  \n"
```

だけ。

# Markdown的な正しい状態

改行テストはこう書くべき。

```
これは同一段落の文章です。  ここで改行しています。  しかし段落は続いています。
```

段落は

```
これは段落Aです。これは段落Bです。
```

# SoulArchive 的に一番安全なルール

ログ保存なら **これをおすすめする**。

### 改行

```
text\n
```

だけにする

（hard break使わない）

### 段落

```
\n\n
```

理由

- Markdownレンダラ差異を回避
- trim事故を防ぐ
- Git diff が綺麗
- LLMが読みやすい
